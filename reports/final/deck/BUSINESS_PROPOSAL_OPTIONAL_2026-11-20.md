# A cooking-state API for recipe platforms

Recipe platforms, smart-appliance makers, meal-kit providers and nutrition apps could use an API that explains which evidence applies to a cooking step. The service would accept a recipe and a question and return a structured state trace, the evidence basis, a response and a reason when the evidence runs out.

A pilot would integrate the API into a recipe platform's recipe editor. An editor could inspect ingredient and process changes, compare the conditions against the source, and see what the claim packet permits. The platform could choose the language model while keeping the same deterministic state and evidence rules.

The signed Explorer and local console demonstrate the proposed interaction. The Tomato A–D examples show how ingredients change the route. The development evidence remains partial and the business case requires buyer interviews and a pilot with rights to use the partner's recipes.

The first pilot would define a human-verified reference set, collect cook feedback on abstention and advice, and agree on data rights with the recipe partner. Ingredient coverage, evidence gaps and unknown mixture properties determine where the pilot can offer useful answers.
